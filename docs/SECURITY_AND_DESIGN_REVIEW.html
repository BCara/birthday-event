Critical

CRITICAL C1 — Any guest could read/list/edit/delete every RSVP ✅ fixed

firestore.rules (rsvps block)
  • The list rule let any guest download all RSVP documents for a published event (names, ages, emails, phones, dietary notes) — a bulk PII-harvesting hole. The "Already RSVP'd?" lookup relied on this (downloaded the whole collection and filtered client-side).
  • The get/update/delete rule ended in || true, so anyone could modify or delete any RSVP.

Fix: list and delete are now host-only. Guest "find my RSVP" moved to a server-side Cloud Function (lookupRsvp) that requires child name and matching email/phone before returning anything. get/update remain open as a deliberate bearer-token model (must know the unguessable 20-char document ID — e.g. own localStorage or edit link).

Residual risk (documented): holding an RSVP's document ID grants read/edit of that one RSVP — the intended "edit-link" design. A fully locked-down version routes all reads/writes through Cloud Functions (see F1).

CRITICAL C2 — Storage was world-readable AND world-writable ✅ fixed

storage.rules

allow read, write: if true on memories/** and event-photos/** let anyone upload unlimited files of any type/size, and overwrite or delete existing photos/memories.

Fix: uploads are now create-only (no overwrite/delete by clients), restricted to image/* (<15 MB) and video/* (<200 MB). Event-photo uploads additionally require an authenticated user. Host memory deletion still works (it only removes the Firestore doc).

CRITICAL C3 — memories collection had no Firestore rule ✅ fixed

firestore.rules

The repo ruleset defined users, events, rsvps then default-deny — the memories collection had no rule, so under these rules every memory read/write is denied. (The live deployment may differ from the repo, which is itself a risk.)

Fix: added an explicit memories rule — public read, validated public create (size caps on text), update/delete host-only.

High

HIGH H1 — RSVP creation is an open email-sending oracle 🟡 partial

firestore.rules (rsvps create) + functions/index.js (onRsvpCreated)

Anyone can create an RSVP doc with an arbitrary email; the function then sends a styled email from the Resend account to that address — usable to spam third parties and the host, and to burn sender reputation.

Mitigated: create is now validated (event must be published; size caps on all text fields and the siblings array) which limits payload abuse.

Follow-up (F2): the real fix is Firebase App Check plus per-event rate limiting. Requires Firebase console setup.

HIGH H2 — Unauthenticated callable functions with no abuse controls 🟡 partial

functions/index.js — contactOrganiser, submitGlobalContactForm

No auth, no captcha, no rate limit, no length caps → spam relays to host/admin inboxes.

Mitigated: added field validation and length caps (name ≤100, contact ≤200, message ≤4000, basic email shape) to both functions.

Follow-up (F2): App Check + rate limiting.

HIGH H3 — No email verification and no password reset ✅ fixed

AuthContext.jsx, SignupPage.jsx, LoginPage.jsx

Signup never verified emails; there was no "Forgot password?" path, so a locked-out host permanently lost their event.

Fix: signup now sends a verification email (non-blocking — does not gate access), minimum password length raised to 8, and a "Forgot password?" flow (sendPasswordResetEmail) added to the login page.

  • F2 — Enable Firebase App Check (reCAPTCHA Enterprise/v3) and enforce on callable functions and Firestore/Storage — the proper fix for H1/H2.

Deployment notes — order matters (live site)

The rules changes depend on the new lookupRsvp function and the rebuilt client. Deploy in this order to avoid breaking the live guest flow. If rules are deployed first, the "Already RSVP'd?" lookup will fail until the client/function catch up.
1. firebase deploy --only functions                 # publishes lookupRsvp + validation
2. npm run build && firebase deploy --only hosting   # client that calls lookupRsvp
3. firebase deploy --only firestore:rules,storage   # locks down access
