A — Security

Critical

CRITICAL C1 — Any guest could read/list/edit/delete every RSVP ✅ fixed (Jun 2026)

firestore.rules (rsvps block)
  • The list rule let any guest download all RSVP documents for a published event (names, ages, emails, phones, dietary notes).
  • The get/update/delete rule ended in || true, so anyone could modify or delete any RSVP.

Fix: list and delete are now host-only. Guest lookup moved server-side to lookupRsvp (requires name + contact match). get/update use a bearer-token model on the unguessable doc ID.

CRITICAL C2 — Storage was world-readable AND world-writable ✅ fixed (Jun 2026)

storage.rules

Unlimited uploads of any type/size; overwrite or delete by anyone. Fixed: create-only, image/video with size caps, host auth required for event photos.

CRITICAL C3 — memories collection had no Firestore rule ✅ fixed (Jun 2026)

firestore.rules

No rule = default-deny blocked all guest memory submissions. Fixed: explicit rule with host-only read, validated guest create, host-only update/delete.

CRITICAL C4 — Contact functions are an open spam relay ⬜ to do

functions/index.js — contactOrganiser (L390), submitGlobalContactForm (L1063)

Both are https.onCall with no auth check, no App Check, no rate limiting. A script loop of a few thousand calls drains the Resend sending quota (blocking all legitimate RSVP/host mail) and runs up cost. contactOrganiser additionally lets an attacker email any host with arbitrary content given any published eventId (all published events are queryable by slug).

Note: This was previously listed as H2 (partial mitigations: field validation + length caps applied). Elevated to Critical because App Check was never added and the exploit path remains fully open. parseRsvpMessage is correctly gated with an auth check; these two should be too.

Fix required: Add auth check (context.auth) + Firebase App Check (reCAPTCHA v3 or Enterprise) + per-IP/per-event rate limiting via a Firestore counter or Redis.

High

HIGH H1 — RSVP creation is an open email-sending oracle 🟡 partial (Jun 2026)

firestore.rules (rsvps create) + functions/index.js (onRsvpCreated)

Anyone can create an RSVP doc with an arbitrary email; the function sends a styled email from the Resend account to that address.

Mitigated: create is now validated (event must be published; size caps on all text fields and siblings array).

Follow-up: Firebase App Check + per-event rate limiting (see F2).

HIGH H2 — RSVP update rule allows self-approval and cross-event injection ⬜ to do

firestore.rules (rsvps update, L54) + RSVPPage.jsx:426

The update rule calls rsvpWithinLimits() which only checks field sizes — it does not pin eventId to its existing value, nor restrict attending or status. A guest holding their own bearer-token RSVP ID can directly call Firestore to:

  • Self-approve a lockdown RSVP: flip attending: 'needs_approval' → true. The client's lockdown guard is only enforced in RSVPPage.jsx:383 for new submissions, not edits. This also triggers onRsvpApproved sending the guest a "You're confirmed!" email.
  • Cross-event data poisoning: change eventId to any other published event's ID. That host's GuestListPage query now returns the attacker's doc, injecting arbitrary guest entries, dietary/comments into a stranger's list.

Fix in rules: add request.resource.data.eventId == resource.data.eventId on update, and validate that attending can only transition from needs_approval if isEventHost(resource.data.eventId).

HIGH H3 — events create doesn't bind hostId to the caller — identity spoofing ⬜ to do

firestore.rules (events create, L40) + CreateEventPage.jsx:114

allow create: if request.auth != null — any signed-up user can create an event doc with hostId = a victim's UID. Consequences: onEventCreated (L16) emails the victim "Your Birthday Event is Ready!" (phishing), and ownership attributes content to their account. published is also unconstrained, enabling arbitrary public spam event pages.

Fix: require request.resource.data.hostId == request.auth.uid on create. Also freeze hostId on update with request.resource.data.hostId == resource.data.hostId.

Was M1 in prior review; elevated to High now that the attack path is confirmed in detail.

HIGH H4 — No email verification; no password reset ✅ fixed (Jun 2026)

AuthContext.jsx, SignupPage.jsx, LoginPage.jsx

Signup never verified emails; no "Forgot password?" path. Fixed: verification email on signup (non-blocking), minimum password raised to 8 chars, password reset added via sendPasswordResetEmail.

Medium

MED M1 — Memory docs accept arbitrary mediaUrl and uncapped media array ⬜ to do

firestore.rules (memories create, L73) + MemoriesPage.jsx:27,42,60

The memories create rule validates only message and authorName sizes. A crafted addDoc can set mediaUrl/media[].url to any URL — the host dashboard renders it in <img>/<video> and fetch()es it on "Save", enabling a tracking beacon / SSRF-from-host-browser vector. An unbounded media array can bloat docs to Firestore's 1 MB limit. A guest can also set eventId to any published event, injecting a memory into a stranger's capsule (and incrementing their memoryCount).

Fix: whitelist mediaUrl/media[].url to your Storage bucket domain in rules; cap media array size (e.g. 30); pin eventId on create to a published event the doc is being submitted against.

MED M2 — No hosting security headers ⬜ to do

firebase.json (hosting block)

No headers array in firebase.json. Missing: X-Frame-Options: DENY (clickjacking of /login and dashboard), Content-Security-Policy (defence-in-depth against injected script), Referrer-Policy: no-referrer (the RSVP bearer token travels in the URL — a loose referrer policy exposes it via referrer headers and link history), X-Content-Type-Options: nosniff, and HSTS.

Fix: add a headers glob to firebase.json hosting. No code deploy needed — rules-only change.

MED M3 — lookupRsvp has no rate limiting or App Check ⬜ to do

functions/index.js:1153

Public unauthenticated callable. Each call scans the full RSVP collection for the event (db.collection('rsvps').where('eventId','==',…).get(), L1186) and filters in-memory. Repeated unauthenticated calls drive Firestore read costs. An attacker knowing a child's name can brute-force the contact field (email/phone) with no lockout — a match returns full RSVP PII (parent name, email, phone, dietary, comments).

Fix: App Check + per-event/IP rate limiting (Firestore counter or Redis). Also move to a server-side indexed query rather than full-collection scan.

MED M4 — Admin/notification emails interpolated user input unescaped✅ fixed (Jun 2026)

onEventCreated / onUserCreated — HTML injection into our own inboxes. Now escaped via escapeHtml().

MED M5 — contactOrganiser used /\\n/g instead of /\n/g✅ fixed (Jun 2026)

Newline-to-<br> conversion matched a literal backslash-n. Fixed.

MED M6 — Event password stored in plaintext on the public event doc⬜ to do

CreateEventPage, EventManagePage, RsvpSettingsModal: the eventPassword field is collected, saved, and sits on a publicly-readable event doc (all published events are readable by anyone). The guest-side code never checks it — the feature is UI-only. Either remove the UI and the field, or implement the check server-side and never expose the raw password to the client.

MED M7 — Slug uniqueness is check-then-write (TOCTOU race)⬜ to do

Use a slugs/{slug} reservation doc in a transaction, or enforce uniqueness in a Cloud Function.

MED M8 — Google Maps API key shipped to the client⬜ verify

LocationInput.jsx. Acceptable only if HTTP-referrer-restricted + API-scope-restricted in Google Cloud console — verify this is configured.

MED M9 — /dev/themes route ships in production⬜ to do

router.jsx:120. The page renders only mock data so no real data leak, but it should be gated behind import.meta.env.DEV.

MED M10 — Hardcoded personal emails in Cloud Functions⬜ to do

Admin/notify addresses hard-coded in functions/index.js. Move to Firebase environment config or Secret Manager.

Shared-device leakage. Acceptable design tradeoff given no-login guest flow, but document the risk.

LOW L2 — QR codes generated via third-party api.qrserver.com⬜

Leaks the invite URL to a third party. Use the already-bundled qrcode.react (used in CapsuleDisplayPage.jsx:9) everywhere instead.

See bug B-M9 below — literal \n\n appears in exported calendar descriptions.

LOW L4 — No CSP / noindex on auth pages⬜

Covered by M2 (hosting headers). /login already has noindex; /signup is missing it.

Causes a blank flash on dashboard load. Return a loading spinner instead.

B — Correctness Bugs

Bugs that cause wrong, broken, or data-corrupting behaviour. These are defects, not missing features.

High — wrong in normal use

HIGH B-H1 — Portal always says "3rd Birthday" regardless of child's real age⬜ to do

EventLandingPage.jsx:331, LeaveMemoryPage.jsx:148, CapsuleDisplayPage.jsx:110

All three render event.childAge ? ord(event.childAge) : '3rd', but childAge is never written to the events collection — CreateEventPage and EventManagePage don't set it. Every published event shows "…'s 3rd Birthday" regardless of the child's actual age or whether it's a birthday at all.

HIGH B-H2 — Developer placeholder data shown to real guests when fields are blank⬜ to do

EventLandingPage.jsx:330,355,546,595,603,380,733,749,1000 · GuestListPage.jsx:297-298,626

When a host leaves optional fields blank, guests see another family's details as facts:

  • Child name fallback: "Robin's"
  • End time fallback: "2:00 PM" (invented time shown as scheduled)
  • Location fallback: "Myuna Farm"
  • Address fallback: "400 Myuna Farm Rd, Dural NSW 2158" — a real street address sent to guests as if it's their venue
  • Host name fallback: "Cara" ("Contact Cara", "MESSAGE CARA")

The dashboard also flashes these values while event is still null on load.

HIGH B-H3 — Editing a pending RSVP silently self-approves it and fires "You're confirmed!" email⬜ to do

RSVPPage.jsx:383,414,426 + functions/index.js:857

The needs_approval path (RSVPPage.jsx:383) only runs when !existingDocId. If a lockdown guest reopens the RSVP form, finalAttending = isAttending = true is written via updateDoc, flipping their status to confirmed without host action. onRsvpApproved then emails them "You're In!" — the host's approval gate is fully bypassed in the edit flow. (Also a security finding — requires both client fix and rules fix.)

HIGH B-H4 — "Approve" on a declining guest sends an "at-capacity" rejection email⬜ to do

GuestListPage.jsx:448, RSVPPage.jsx:398-403, functions/index.js:972

Because RSVPPage.jsx:398 routes all lockdown submissions into needs_approval — including guests who answered "No, can't make it" (intendedAttending: false) — the host's Approve action sets attending: false. This triggers onRsvpDeclined and emails the guest "the party has reached capacity." A declining guest should never enter the approval queue.

HIGH B-H5 — Accent colour picker on Create Event is broken (transparent swatches, writes wrong value)⬜ to do

CreateEventPage.jsx:264

Iterates Object.entries(THEME_COLOR_SCHEMES) at the wrong nesting level — keys are theme names ('kids-dino'…), not colour configs. Result: 5 transparent/invisible swatch buttons, and clicking one stores a theme key as the themeColor value. getTheme() silently falls back to default, so colour selection during creation has no effect. EventManagePage does this correctly (iterates the inner THEME_COLOR_SCHEMES['kids-${theme}'] object).

HIGH B-H6 — Dead "Send Reminder", "Filter", and "•••" buttons⬜ to do

GuestListPage.jsx:880-883, 965-967, 1152-1154

Rendered as normal clickable buttons with no onClick handler. Hosts click them and nothing happens — no loading state, no toast, no "coming soon" messaging. Wire up or replace with a disabled state and tooltip.

Medium — wrong in edge cases or silently broken

MED B-M1 — EventManagePage form wipes unsaved edits when the event doc updates remotely⬜

EventManagePage.jsx:298-354

The onSnapshot callback unconditionally resets all form fields on every snapshot. External writes (e.g. a guest uploads a memory, bumping memoryCount; a sibling page saves RSVP settings) cause the host's in-progress edits to be silently discarded. The childName === '' guard at :307 uses a stale closure (deps [eventId, navigate]) and is always true, so it provides no protection.

MED B-M2 — Contact emails report success even when Resend rejects them⬜

functions/index.js:480-494, 1126-1140

contactOrganiser and submitGlobalContactForm never check r.ok on the Resend API response. A 4xx/5xx (bad key, rate limit, unverified domain) still returns { success: true } — guests see "Message sent!" while nothing was delivered. Given the domain-verification outage already experienced, this should be a monitored error.

MED B-M3 — Editing an RSVP overwrites its original createdAt⬜

RSVPPage.jsx:421,426

rsvpData includes createdAt: serverTimestamp() and is passed directly to updateDoc. Every edit resets the submission timestamp: the guest list (sorted by createdAt) reorders, and the "Date" column and CSV export show the last-edit date as the RSVP date.

MED B-M4 — lookupRsvp returns pending/imported guests as "YOU'RE GOING!"⬜

functions/index.js:1215 + EventLandingPage.jsx:225-227, RSVPPage.jsx:278

isAttending: d.isAttending ?? true — imported guests (attending: 'pending', no isAttending field) and lockdown-pending guests come back as isAttending: true. The client stores rsvp_status = 'yes' and the portal renders "🤍 YOU'RE GOING! 🤍" for a guest who is awaiting approval or never formally RSVPed.

MED B-M5 — 404 page text is invisible in the light theme⬜

NotFound.jsx (heading: #fff, body: rgba(255,255,255,0.5))

MainLayout forces data-theme="light" where --kb-bg is #FFF9F2. White text on cream background — heading and body copy are effectively unreadable. Styles were written for the dark palette.

MED B-M6 — CSV export labels every non-yes status as "No"⬜

GuestListPage.jsx:180-187

isAttending ? 'Yes' : 'No' — imported 'pending', 'maybe', and 'needs_approval' guests all export as Attending: No, which is inaccurate data in the host's exported list (the on-screen table distinguishes these statuses).

MED B-M7 — Bulk import has no error handling⬜

GuestListPage.jsx:390-420

Sequential await addDoc loop with no try/catch. A mid-import Firestore failure (offline, rule rejection) rejects unhandled — no error toast, modal stays open, partial import with no feedback or rollback.

MED B-M8 — ICS description renders literal \n\n instead of blank lines⬜

calendarUtils.js (generateICS)

fullDesc += '\\n\\n' inserts literal backslash-n characters before esc() runs; esc() then doubles the backslashes. Calendar apps render the text …description\n\nView event details: … with visible "\n\n" when both a description and URL are present. Also: the Google Calendar all-day case uses dates=${d}/${d} — Google treats the end date as exclusive, so this produces a zero-length event.

MED B-M9 — handleSaveGuest writes UI-only fields into Firestore⬜

GuestListPage.jsx:522-523

updateDoc(guestDocRef, updatedGuest) spreads the whole row object, persisting junk fields id, isSiblingRow, and mainGuestId into RSVP documents. Harmless today but pollutes documents and risks future field collisions.

stripe.js:19 + BillingPage.jsx

LOW B-L3 — guestEstimate split uses Math.floor for both halves on manage page⬜

EventManagePage.jsx:341-342

Comment even says "Fixed: should use ceil" but the code still uses Math.floor for both kids and adults. For an odd legacy guestEstimate, saving shows a total one lower than the guest list displays.

LOW B-L4 — LeaveMemoryPage object-URL cleanup is a stale closure (memory leak)⬜

LeaveMemoryPage.jsx:48-50

Unmount cleanup iterates files captured from the first render (always [], deps []). Preview object URLs are never revoked on unmount despite the comment claiming they are.

LOW B-L5 — Guest confirmation email shows "sorry you can't make it" banner for "maybe" RSVPs⬜

functions/index.js:317-321

Status banner only handles needsApproval/isAttending; attending === 'maybe' falls through to the decline banner. Mostly unreachable today (the client form only produces yes/no/needs_approval).

LOW B-L6 — GuestListPage event date parsed as UTC (off-by-one day west of UTC)⬜

GuestListPage.jsx:297

new Date(event.date) on a bare YYYY-MM-DD string parses as UTC midnight, then formats in local time. In any timezone west of UTC (e.g. AEST in winter) the banner shows the previous day. Every other page correctly appends 'T00:00:00'.

LOW B-L7 — ThemedPage doesn't swap font links on theme change⬜

ThemedPage.jsx:19-27

Debug statements log event/RSVP data to the browser console in production. Remove before next deploy.

C — UX & Requirements Gaps

Missing or broken user journeys — not cosmetic preferences. Verified in code; only gaps not already on the active roadmap are listed.

High — broken journeys or compliance-grade gaps

HIGH C-H1 — Lost/cross-device RSVP recovery is effectively broken⬜ to do

EventLandingPage.jsx:292 (dead branch) + functions/index.js:289,369

The confirmation email tells guests: "Visit the invite page and use the 'Already RSVP'd?' lookup." That UI is in the dead invitation branch (B-L1) and is entirely unreachable. The reachable portal branch has no lookup entry point. The "Already RSVP'd?" link in RSVPPage.jsx:708 navigates to /portal which also has no lookup — a dead-end loop.

Cheapest fix (highest value): add ?rsvpId={id} to the confirmation email's "View your RSVP" button. This is a one-line change in functions/index.js:289 that requires only a functions deploy. It solves lost-link, cross-device access, and duplicate RSVPs for all guests who provided an email.

HIGH C-H2 — Multi-photo memories are silently truncated to one photo in the host capsule⬜ to do

MemoriesPage.jsx:42,73,125-144 · LeaveMemoryPage.jsx:108-117

Guests can upload up to 30 files saved as a media array. The host dashboard, Save button, and text export all read only memory.mediaUrl || memory.photoUrl (i.e. media[0]). Files 2–30 are invisible to the host. The Memory Capsule's core day-of payload is being lost.

HIGH C-H3 — Module toggles and RSVP settings are not enforced on the guest side⬜ to do

EventLandingPage.jsx:398 · RSVPPage.jsx (no rsvpEnabled check) · LeaveMemoryPage.jsx (no memoriesEnabled check)
  • rsvpEnabled: false: portal still shows "RSVP NOW" and RSVPPage has no guard — guests can still submit RSVPs when the host has turned RSVP off.
  • memoriesEnabled + window dates: gates the link in EventLandingPage but not the page itself — /:slug/memories/new accepts submissions any time for any published event since rules only require published == true.
  • rsvpByDate: displayed as "Please respond by…" but never blocks submission after the date passes.
  • Capacity: shown nowhere enforced — the auto-decline email claims "party has reached capacity" as a fact the system doesn't track.

HIGH C-H4 — No event cancel, reschedule, or delete — and no guest notification when details change⬜ to do

EventManagePage.jsx (no delete/unpublish action) + PrivacyPolicyPage.jsx:66,68
  • There is no way to unpublish, cancel, or delete an event. Events are created as published: true (CreateEventPage.jsx:146) and stay public forever.
  • When a host edits date/time/venue, no guests are notified — guests who RSVP'd and added a calendar entry will go to the wrong place.
  • A host is never notified when a guest changes their RSVP (onRsvpCreated is create-only; a yes→no flip is silent).
  • Compliance gap: the Privacy Policy promises "If you delete an event, its associated guest and RSVP data is also deleted" and "we can delete all your data on account closure" (PrivacyPolicyPage.jsx:66,68). Neither feature exists. Given the app collects children's names, ages, and allergies, these are unfulfillable compliance promises under the Privacy Act 1988.

HIGH C-H5 — No post-event journey (capsule delivery, thank-yous)⬜ to do

MemoriesPage.jsx:125-144 · EventLandingPage.jsx (no post-event state)

After the party: no thank-you action, no "your capsule is ready" host notification, export is a .txt of links (no zip of photos). Guests visiting the event page after the date see the same page with no post-event messaging. Given the Memory Capsule is the intended paid differentiator, the post-event journey is the roadmap's biggest uncovered area.

HIGH C-H6 — Monetisation is dead code — privacy policy describes it as live⬜ to do

BillingPage.jsx:54,70,87 · stripe.js:19 · PrivacyPolicyPage.jsx:67

Stripe checkout calls a Cloud Function that does not exist (B-L2). Upgrade buttons are disabled with "COMING SOON". Yet the privacy policy describes Memory Capsule as a "paid feature" with retention "for the duration of your active subscription." Guest limits advertised on the billing page (e.g. "Up to 50 guests") are not enforced anywhere. The marketing copy is ahead of the product.

Medium — suboptimal but not broken

MED C-M1 — Declining RSVP requires completing the full 4-step wizard⬜

A guest answering "No, can't make it" must still enter child name, parent contact, and details. A one-tap decline with optional name is standard for invitation apps.

MED C-M2 — No duplicate RSVP detection (without lockdown enabled)⬜

RSVPPage.jsx:383-397

The lookupRsvp dedup check only runs when requireGuestMatch is true (off by default). On a new device the guest sees "RSVP NOW", submits again, and creates a second doc. The host sees two rows with no indication they're the same family.

MED C-M3 — Date/locale inconsistency (en-US on an Australian product)⬜

RSVPPage.jsx:486,499 · EventLandingPage.jsx:157

Guest pages format dates as en-US ("June 21") while emails and dashboard use en-AU. The .ics export uses floating time with no TZID — a guest in a different timezone sees the countdown/formatting in their own timezone with no indication.

MED C-M4 — Aggregate dietary/allergy view is absent despite homepage claiming "flags dietary alerts"⬜

GuestListPage.jsx:840-858 vs. HomePage.jsx:26,146

The marketing home page claims a "3 Dietary alerts" metric. The guest list has no dietary summary panel — only per-row coral text and raw CSV export. An aggregated panel (modelled after the existing age-breakdown pills) would close this claims-vs-reality gap and is high value for the host on the day.

MED C-M5 — Docs describe features that no longer exist in the codebase⬜

docs/USER_FLOWS.md · router.jsx

USER_FLOWS.md Flow 10 describes /slug/live with a live approval slideshow and MemoriesPage approve/unapprove toggles — the route doesn't exist in router.jsx and the components have no such controls. Flow 11 says "No email sent on decline" — stale; onRsvpDeclined exists and sends one. Signup password minimum is documented as 6 chars; the code requires 8.

Follow-ups requiring console or product decisions

  • F1 — Route all guest RSVP reads/writes through Cloud Functions (makes approval/lockdown/deadline/module toggles server-authoritative; eliminates bearer-token residual from A-C1).
  • F2 — Enable Firebase App Check (reCAPTCHA Enterprise or v3) and enforce on callable functions and Firestore/Storage. This is the correct fix for A-C4, A-H1, A-M3 and prevents unauthenticated API abuse at scale.
  • F3 — Add @firebase/rules-unit-testing tests so a regression like the original || true can never ship silently again.
  • F4 — Memory moderation policy: memories are currently auto-approved and visible in the host capsule within seconds of upload. Decide on a moderation step if needed.
  • F5 — Data retention / deletion: implement event delete with cascade cleanup of rsvps, memories, and Storage files to fulfil the privacy policy promise. This is also needed for account closure. Consider a scheduled Cloud Function to purge events older than N months after their date.
  • F6 — Stripe: complete createStripeCheckoutSession Cloud Function and webhook handler before enabling the upgrade buttons (see B-L2 / C-H6).

Deployment notes — order matters on a live site

Rules changes that restrict previously-open access (e.g. A-H2, A-H3) should always be deployed after the client that handles the new errors, not before, to avoid breaking the live guest flow.
# Safe deploy order for rules hardening (A-H2, A-H3, A-M1, A-M2):
1. npm run build && firebase deploy --only hosting   # client-side fixes first
2. firebase deploy --only functions                  # updated lookupRsvp, email fixes
3. firebase deploy --only firestore:rules,storage    # lock down access last

# Security headers (A-M2) — firebase.json only, no code rebuild needed:
firebase deploy --only hosting
