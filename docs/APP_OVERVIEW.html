What is Tiny Party Portal?

Tiny Party Portal is a web app for planning a child's birthday party. A parent (the host) creates a themed event page, shares a link or QR code, and guests reply (RSVP) in seconds — no app to download, no account needed.

Around that core, the app offers three optional pieces per event:

  • Web invite — the always-on themed page with date, time, location and details.
  • RSVP — guests confirm attendance, dietary needs, siblings and more; the host sees a live guest list.
  • Memory Capsule — a private place for guests to add photos and messages from the day, collected only for the host and child.
It is a single-page web app (React) hosted on Firebase. There is nothing to install — everything runs in the browser.
2

Who Uses It

Host

The parent organising the party. Signs in, creates and configures the event, shares it, manages RSVPs, and views the Memory Capsule. The only person who needs an account.

Guest

An invited family. Opens the link, views the invite, RSVPs, and (optionally) adds a memory. Never logs in — they're identified by the link they hold.

Admin

The Tiny Party Portal operator. Receives notification emails (new signups, new events) but doesn't act inside a host's event.

System

Background Cloud Functions that send emails, look up RSVPs, parse pasted messages, and serve social-share previews.

Interaction Flows

Each flow below explains what happens and why, with a diagram and a link to the matching tests in the Functional Testing Guide.

① Sign Up & Onboarding Host

A new host creates an account with Google or an email + password. On success they land on their dashboard and receive a welcome email; the admin is notified of the new signup.

  1. Visit the site → choose Sign Up.
  2. Sign up with Google (one tap) or email + password (6+ characters).
  3. Account is created → redirected to /dashboard.
  4. System sends a welcome email to the host and a notification to the admin.
✓ Tested in → Block 1: Authentication

② Create an Event Host

The host fills in the essentials (child's name, date), picks a theme and colour, and the event is saved. Two emails go out: a confirmation to the host and a notification to the admin. If the chosen name clashes with an existing event, the slug gets a number suffix.

flowchart TD A(["+ New Party"]) --> B["Enter child name, date and details"] B --> C["Pick theme and colour"] C --> D["Click Create Party"] D --> E{"Required fields valid?"} E -- No --> B E -- Yes --> F["Event saved in Firestore"] F --> G["Open event management page"] F --> H["Host confirmation + admin notification emails"]
✓ Tested in → Block 2: Create Event

③ Configure the Event & Modules Host

On the management page the host fine-tunes everything: photo, date/time, location, schedule, gift info, and the module bar at the top. Web is always on; RSVP and Memory Capsule are toggles that reveal their own settings when switched on. A live preview reflects changes.

  • RSVP settings — choose which questions guests answer (age, adults, dietary, siblings, whether parents stay or drop off).
  • Memory Capsule — title, guest message, and optional open/close dates.
✓ Tested in → Block 3: Event Management

④ Share the Invite Host

The host shares the event link, a QR code, or a WhatsApp message. The link adapts to which modules are on — if RSVP is enabled it points to the RSVP entry, otherwise straight to the info portal. A special /share/{slug} link produces a rich preview card (photo + details) when pasted into WhatsApp, iMessage or social apps, then forwards the recipient to the real invite.

flowchart TD A["Host copies the share link"] --> B{"Shared where?"} B -- WhatsApp / iMessage / social --> C["eventShareMeta serves preview card"] C --> D["Recipient taps card"] D --> E["Forwarded to the invite page"] B -- Direct link / QR --> E["Guest opens /slug"]
✓ Tested in → Block 12: Share Link & Social Preview

⑤ Guest Views the Invite Guest

The guest opens /{slug} and sees the themed invitation with all the details, a countdown, and add-to-calendar / map buttons. If they've already RSVP'd (remembered on their device), they see the portal instead. If they're on a new device, a "Find your RSVP" lookup restores access.

✓ Tested in → Block 4: Guest Invite / Landing

⑥ Guest RSVPs Guest

A short, four-step form: attendance → child info → parent contact → details. Guests can reply yes or no, add siblings, and give an email or phone. On submit they see a confirmation (with confetti if attending), the host is emailed the new RSVP, and the guest gets a confirmation email if they provided one.

flowchart TD A(["RSVP form"]) --> B["Step 1: Attending?"] B --> C["Step 2: Child info + siblings"] C --> D["Step 3: Parent name + email or phone"] D --> E["Step 4: Details: adults, dietary, stay/drop-off"] E --> F["Submit"] F --> G["Success screen"] F --> H["Host email: New RSVP"] F --> I["Guest confirmation email (if email given)"]
✓ Tested in → Block 5: RSVP Form

⑦ Approval-Required RSVP Host Guest

If the host turns on Lock RSVPs, new replies arrive as Needs Approval instead of going straight through. The guest sees a "request submitted" screen; the host gets an "action required" email and approves or declines from the guest list. Approving sends the guest a confirmation. Guests who were already approved can edit their RSVP without needing re-approval.

flowchart TD A["Guest submits under lock"] --> B["Saved as Needs Approval"] B --> C["Guest: request submitted, no confetti"] B --> D["Host email: Action Required"] D --> E{"Host decision"} E -- Approve --> F["Confirmed → guest emailed You're In"] E -- Decline --> G["Marked Not Attending → no email"]
✓ Tested in → Block 5A: Approval-Required RSVP

⑧ The Event Portal Guest

After RSVP'ing, the guest sees the portal: their attending status, a live countdown, the party schedule, location with maps, gift information (only for attending guests), and a way to contact the host. It's the "everything you need to know" view in the run-up to the day.

✓ Tested in → Block 6: Event Portal

⑨ Managing the Guest List Host

The host's RSVP dashboard shows headcount metric cards (Going / Maybe / Declined / Needs Approval), search and filtering, and tools to add, edit, import (CSV), or export guests. Magic Paste turns a pasted message ("Zara and her brother Tom will come") into a structured RSVP using AI. Manually added or imported guests do not trigger emails.

✓ Tested in → Block 7: Guest List Management

⑩ The Memory Capsule Host Guest

When enabled, guests can add photos, videos and messages — but the capsule is private: a guest submits "blind" and never sees anyone else's contribution. Only the host views the collection (and can download or export it) for the child to look back on.

The entry point on the guest page is deliberately understated before the event (a small footer link, away from the RSVP) and becomes prominent on the day (a card near the top), when people are most likely to share. Optional open/close dates control the window.

flowchart TD A(["Guest on /slug"]) --> B{"Capsule on and in window?"} B -- No --> Z["No entry point"] B -- Yes --> C{"Event day reached?"} C -- Before --> D["Subtle footer link"] C -- On / after --> E["Prominent card near top"] D --> F["Submit a memory (name + message/media)"] E --> F F --> G["Saved privately + success screen"] G --> H["Host views in private capsule; guest sees nothing else"]:::host classDef host fill:#ede9fe,stroke:#8b5cf6,color:#4c1d95;
Privacy by design: there is no public memory wall and no live slideshow. Submissions are readable only by the owning host (enforced by security rules), and uploaded files use unguessable paths.
✓ Tested in → Block 8: Memory Capsule

⑪ Printable Invite Host

The host can open a print-ready invitation card with a QR code and download it as a PDF or image, or print it. Paper size (A5/A4) and a themed or white background are set via URL options.

✓ Tested in → Block 9: Printable Invite

Under the Hood

Technology

  • Frontend: React + Vite single-page app. All UI runs in the browser.
  • Backend: Firebase — Auth (host login), Firestore (data), Storage (photos/videos), Cloud Functions (emails, lookups, share previews), Hosting (serves the site).
  • Email: sent from Cloud Functions on key events.

Data Model (Firestore)

CollectionHoldsWho can read
usersHost account profileThat host only
eventsAll event settings (details, theme, modules, RSVP & capsule config)Owning host always; anyone if the event is published
rsvpsOne record per guest replyOwning host (full list); a guest can read/edit their own via its unguessable ID
memoriesGuest photos, videos and messagesOwning host only — guests can create but never read

Files live in Storage: event-photos/{eventId}/… (host uploads) and memories/{eventId}/… (guest uploads, unguessable filenames, size/type limited).

How Access is Kept Safe (in plain terms)

  • Hosts only touch their own events. The rules check that the logged-in user owns the event.
  • Guests don't log in. Their RSVP link contains an unguessable ID that acts like a ticket — holding it lets them see and edit only that one RSVP.
  • Published events are public to read so guests can open the invite, but only the host can list all RSVPs (no bulk harvesting of contact details).
  • The Memory Capsule is private. Anyone can submit to a published event, but only the owning host can read submissions.
